# Akwaaba

Pre-booked airport pickups in Ghana from **Kotoka International Airport, Accra (ACC)** and **Prempeh I International Airport, Kumasi (KMS)**. A service of **Astrovenza Ventures** (astrovenzav@gmail.com).

## Money model

- **Travellers book for free and pay the driver directly when they meet**, in cash or by mobile money to the driver's own number. No advance payment, no deposit.
- **Drivers keep 100% of every fare.**
- **Astrovenza Ventures collects only the GHS 100 monthly driver subscription**, paid through Paystack. No fare money ever passes through Akwaaba, so there are no fare refunds, chargebacks or payouts to manage.

## How a booking works

1. The traveller chooses the **airport** they are landing at (Accra or Kumasi), then a drop-off **area** from that airport's list, and types the address or a nearby landmark.
2. The **server** looks up the area's zone for that airport and prices the trip in whole cedis. Each airport has its own zones and fares. The browser never sends a price.
3. One database transaction reserves a driver who is **based at that airport**, approved, has an **active subscription**, drives the right vehicle size, and is free within 3 hours of the landing time. The booking is confirmed straight away with the driver's name, car, plate and WhatsApp number.
4. The traveller taps **Open WhatsApp chat with your driver** (a ready-written message with the booking code opens) and sends their exact location with WhatsApp's Location option, or shares the place from the Google Maps app.
5. The driver opens that location in WhatsApp to navigate with their own Google Maps app. The driver app also has WhatsApp and call buttons for the passenger, and a link to navigate to the airport.
6. The traveller pays the driver on arrival. The driver taps through: at meeting point, passenger met, start trip, complete.
7. **No-shows:** if the traveller has not appeared 60 minutes after the scheduled landing, the driver can record a no-show, which frees them for other pickups.

## Protections

- Prices and zones are worked out on the server only; extra fields sent by a browser are ignored.
- Subscription payments are re-checked with Paystack (amount GHS 100, currency GHS) before anything is applied, and each payment is applied exactly once, in one database transaction.
- Webhooks must carry a valid Paystack signature (HMAC SHA512, constant-time check).
- Drivers can only see and update their own trips, one step forward at a time.
- Drivers without an active subscription, or not yet approved, receive no pickups (enforced in the database).
- Row level security on every table; the service role key and Paystack secret key exist only on the server.
- Security headers on every page, including a content security policy that allows scripts, styles and fonts from this site only, and connections only to Supabase.
- Generic errors to users; real errors in Vercel logs; secrets never logged.

## Setup

### 1. Supabase (database and sign-in)
1. Create a project in West Europe (London), `eu-west-2`, to match the server region in `vercel.json`. In **SQL Editor**, run `supabase/schema.sql`.
2. **Authentication > Sign In / Providers**: keep **Email** on (drivers and staff both sign in by email). Phone/SMS is optional and paid; leave it off until you want SMS codes.
3. **Authentication > Multi-Factor**: enable **TOTP** for staff.
4. **Authentication > Emails > SMTP Settings**: turn on custom SMTP (Supabase's built-in sender only reaches your own team's addresses). Free option: Gmail, host `smtp.gmail.com`, port `465`, user `astrovenzav@gmail.com`, password = a Google **app password**. Then in **Emails > Templates > Magic Link**, make the message show the code: `Your Akwaaba sign-in code is {{ .Token }}. It expires in 10 minutes. Never share it.`
5. Add each driver after checking their licence, DVLA sticker and vehicle papers: create the user with their **email** in **Authentication > Users** (Add user > Create new user, tick Auto Confirm), then
   ```sql
   insert into drivers (id, name, phone, email, vehicle_type, vehicle_model, plate, base_airport, status)
   select id, 'Kwame Mensah', '+233244112087', email, 'sedan', 'Toyota Corolla', 'GR 4521-22', 'ACC', 'approved'
   from auth.users where email = 'kwame@example.com';
   ```
   Use `'KMS'` as `base_airport` for drivers who work Kumasi. A driver only receives pickups at their base airport. The phone number is still needed: it is the WhatsApp number travellers are given.
6. Staff: create `astrovenzav@gmail.com`, enrol an authenticator app, then
   `insert into staff (user_id, role) select id, 'admin' from auth.users where email = 'astrovenzav@gmail.com';`

### 2. Paystack (Astrovenza Ventures business account, subscriptions only)
1. Use **test keys** first.
2. **Settings > API Keys & Webhooks**: webhook URL `https://YOUR-DOMAIN/api/paystack/webhook`.

### 3. Vercel
1. Put this folder in a **private** GitHub repo and import it in Vercel.
2. Add every value from `.env.example` in **Settings > Environment Variables**. Mark the Paystack secret key and Supabase service role key as **Sensitive**.
3. Deploy. Traveller page: `/`. Driver app: `/driver`.

Tests: `npm install`, then `npm test`, `npm run test:db` and `npm run test:privacy`. Build the policy page and assets locally with `npm run build`.

## Privacy and data protection

The privacy policy is part of the app, not a separate document.

| Where | What it does |
|---|---|
| `/privacy` | The public privacy policy. Built from `docs/privacy-policy.md` by `npm run build` (Vercel runs it on every deploy). Every page footer links to it. |
| `docs/privacy-features.json` | Switches for optional policy clauses (live location, ID verification API, masked calls, flight tracking, SMS, email). Turn one on only when that feature is live, then redeploy. |
| Booking page | Short notice above **Book pickup**, a required "I am 18 or over" box and an optional, unticked marketing box. The server refuses a booking without the 18+ box, or from a page showing an old notice version. |
| Driver app | Before seeing pickups, a driver acknowledges the privacy notice and gives written consent to vetting checks (required), plus an optional marketing choice. Shown again whenever the notice version changes. |
| Database | Traveller name, phone, email and address are encrypted on the server (AES-256-GCM) before they are stored; drivers see them decrypted only for their own trips. Marketing and driver consents go to an append-only ledger. No-shows and blocked duplicate bookings are kept as phone hashes only. |
| Deletion | Daily and monthly jobs remove traveller details 90 days after the trip and clear old records, as section 9 of the policy says. |
| Third parties | Fonts and the sign-in library are served from this site, so visitors' IP addresses go to no one else. Server functions run in London, next to the database (`regions` in `vercel.json`). |

### Setting it up
1. In Supabase **SQL Editor**, run in order: `supabase/schema.sql`, `supabase/migrations/002_privacy.sql`, `supabase/migrations/003_encrypted_bookings.sql`. Enable **pg_cron** (Database > Extensions), then run `004_retention_schedule.sql`.
2. Generate `PII_ENC_KEYS` and `PII_INDEX_KEY` (commands in `.env.example`) and add them to Vercel as **Sensitive**. Keep an offline copy: lost keys mean lost data.
3. Fill every `[●]` in `docs/privacy-policy.md`. A production deploy **fails** while any remain (preview deploys show a yellow "Draft" bar instead).
4. Have Ghana counsel review the policy, then deploy.

### Changing the policy
Edit `docs/privacy-policy.md`. If the change matters to users, raise `**Version:**` in the policy and `PRIVACY_NOTICE_VERSION` in `lib/privacy.js` together (the build and tests check they match), and update the effective date. Drivers are asked to acknowledge the new version on their next sign-in; bookings record the version each traveller saw. Keep a copy of each old version (policy section 16 promises them on request).

### Encrypting existing bookings
Only needed if bookings were taken before `003_encrypted_bookings.sql`: run a one-off script that reads each row's plain-text name, phone, email and address, writes the encrypted columns and `passenger_phone_hash` with `lib/privacy.js`, and sets the plain-text columns to null. Then run `alter table bookings validate constraint bookings_no_plaintext_pii;`.

### Handling requests (access, deletion, marketing opt-out)
Email requests go to astrovenzav@gmail.com. Log each one in `dsar_requests` and reply within 30 days. To find a traveller's bookings, compute their phone hash with `subjectHash()` from `lib/privacy.js`; to delete closed bookings, run `select erase_traveller('<hash>')`. For a marketing opt-out, insert a `consent_events` row with `granted = false`. The full process is in `docs/data-architecture-spec.md`.

## Go-live checklist
- [ ] Full run in Paystack test mode: driver signs in and pays the subscription; traveller books; driver completes the trip; another trip is marked as a no-show.
- [ ] Try to break it: change prices or areas in the browser, replay a subscription webhook, send one without a signature, open or update another driver's trip. All must fail.
- [ ] Real zone fares and the full list of drop-off areas in `zone_fares` for **both** airports. The Kumasi fares are sample values set lower than Accra's because the city is smaller; check them with Kumasi drivers.
- [ ] Recruit and approve drivers based in Kumasi before taking Kumasi bookings. Until then, Kumasi travellers see "no driver available".
- [ ] Rate limiting on `/api/quote` and `/api/bookings/initialize` (Vercel Firewall rules). With free booking, this also stops fake bookings tying up drivers.
- [ ] Driver terms (drivers collect and keep fares; Astrovenza provides bookings for a monthly fee) and passenger terms (pay the driver on arrival; free waiting time; no-show rule).
- [ ] Data Protection Commission registration (names, phone numbers, addresses) before taking real bookings (Act 843 s.53). Fill the policy placeholders, including the registration number.
- [ ] Swap to `sk_live_...`, redeploy, pay one real subscription.

## Notes
- **No-show risk:** with no deposit, a traveller can book and not turn up. Drivers can record a no-show after 60 minutes. A next step is an SMS code to confirm the traveller's phone number when booking, and blocking numbers with repeated no-shows.
- **Night surcharge** (20%, landings 22:00 to 04:59) uses the scheduled landing time the traveller enters. A flight-status service can replace this later.
- **Areas not on the list:** travellers pick the nearest listed area. Add areas to `zone_fares` as requests come in.
- **Another airport later** (for example Tamale or Takoradi): add a row to `airports`, its zones to `zone_fares`, drivers with that `base_airport`, and a button on the booking page.
- **Not built yet:** driver self-registration, the staff Operations web app (bookings overview, fares, areas, driver approval), cancellations, SMS notifications, and the traveller phone check above.
